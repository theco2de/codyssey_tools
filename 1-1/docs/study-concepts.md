# 학습 노트: AI Agent에게 일 제대로 시키는 법

이 과제(Spring 수강생 질문 답변 초안 만들기)를 하면서 만난 개념 11개를 정리한 학습 노트예요.
각 개념은 **정의 → 왜 필요한가 → 이 과제의 사례 → 직접 해 보기 → 자기 점검** 순서예요.
사례는 이 저장소의 문서를 가리켜요. 읽다가 궁금하면 해당 문서를 열어 원문을 확인해 보세요.

> 참고 문서: [model-comparison.md](model-comparison.md) · [system-design.md](system-design.md) · [run-log.md](run-log.md) · [unresolved.md](unresolved.md)

## 학습 순서와 지도

```
과업 정의(1) ─▶ 모델 평가(2) ─▶ 시스템 프롬프트(3) ─▶ Few-shot(4) ─▶ CoT(5)
                                                         │
        기록·재현성(11) ◀─ 프롬프트 한계(10) ◀─ 개선 루프(9) ◀─ 환각·검증(6)
                                                         ▲
                                     멀티턴 문맥(7) ─ 비결정성(8)
```

| 단계 | 개념 | 목표 |
|---|---|---|
| 설계 | 1, 2, 3 | 무엇을 시킬지, 어떻게 판정할지, 어떤 규칙으로 일하게 할지 정한다 |
| 기법 | 4, 5 | 예시와 추론 유도를 언제 쓸지 안다 |
| 검증 | 6, 7, 8 | 틀린 대답, 문맥 끊김, 실행마다 달라지는 결과를 찾는다 |
| 개선 | 9, 10, 11 | 근거를 가지고 고치고, 한계를 기록한다 |

## 1. 과업 정의와 출력 규격

**정의**
LLM에게 일을 맡기기 전에 **입력이 무엇이고 출력이 어떤 모양이어야 하는지**를 정하는 일이에요.

**왜 필요한가**
"잘 답해 줘"라고만 하면 응답의 길이, 구조, 깊이가 매번 달라서 좋은지 나쁜지 판정할 수 없어요.

**이 과제의 사례**
- 입력: 질문 본문, 에러 로그, 환경, 진도 ([system-design.md](system-design.md) §5 입력 템플릿)
- 출력: 원인 추정(1~2문장) → 확인 방법(최대 3단계) → 해결 힌트(코드 3줄 이하) → 함께 볼 개념(1개)
- 분기: 정보가 부족하면 4단 대신 **되묻기 질문만 최대 3개**

**핵심 포인트**
- 출력 규격에는 "문장 수", "단계 수", "줄 수"처럼 **세어서 확인할 수 있는 기준**을 넣어요.
- 예외 상황(정보 부족)에서 어떻게 할지도 미리 정해요.

**직접 해 보기**
다른 과업(예: 복습 퀴즈 생성)을 골라 입력 3가지와 출력 규격(개수 제한 포함)을 써 보세요.

**자기 점검**
1. "친절하게 설명해 줘"는 왜 좋은 출력 규격이 아닐까요?
2. 이 과제에서 "정보가 부족할 때" 규칙이 없었다면 어떤 일이 생겼을까요?

<details><summary>정답 힌트</summary>

1. "친절하다"는 세어서 확인할 수 없어서 지켰는지 판정이 안 돼요.
2. 모델이 추측으로 답했을 거예요. 실제로 Zero-shot은 "스프링 실행이 안 돼요"에 포트, JDK, DB를 추측해 나열했어요.
</details>

## 2. 모델 평가: 루브릭과 정답표

**정의**
- **루브릭**: 점수를 매기는 기준표
- **정답표(ground truth)**: 맞는 답과 틀린 답으로 볼 것을 **결과를 보기 전에** 적어 둔 표

**왜 필요한가**
결과를 본 뒤에 기준을 정하면 마음에 드는 쪽으로 기울어요. 사전에 정해야 공정해요.

**이 과제의 사례** ([model-comparison.md](model-comparison.md) §4~§6)
- 기준 5개: 형식 준수, 사실 정확성, 수준 맞춤, 힌트 우선, 환경 반영
- 정답표에 "틀린 답"도 적음: `javax.servlet-api` 의존성 추가, `required=false`, 구현체 삭제만 제시
- 점수 합계: GPT 22, Gemini 25, Claude 24

**핵심 포인트**
- 점수가 가장 높은 모델이 곧 정답은 아니에요. 이 과제에서는 **남은 약점을 프롬프트로 고칠 수 있는가**로 골랐어요.
  - 고칠 수 있는 것: 문장 수 초과, 어투, 분량
  - 고치기 어려운 것: 명령어 세부 오류처럼 모델의 정확성 문제
- 각 조건을 한 번씩만 실행한 비교는 **표본이 작다**는 한계를 함께 적어요.

**직접 해 보기**
같은 질문 1개를 서로 다른 AI 2개에 넣고, 이 과제의 기준 5개로 1~5점을 매겨 보세요. 정답표는 결과를 보기 전에 먼저 쓰세요.

**자기 점검**
1. 정답표에 "틀린 답으로 볼 것"을 같이 적는 이유는?
2. 합계가 더 높은 모델 대신 점수가 낮은 모델을 고를 수 있는 이유는?

<details><summary>정답 힌트</summary>

1. "그럴듯하지만 틀린 답"을 놓치지 않으려고요. 맞는 답만 적으면 모델이 틀린 방향으로 가도 걸러내기 어려워요.
2. 약점이 프롬프트로 고쳐지는지가 중요하기 때문이에요. 고칠 수 있는 약점은 나중에 해결돼요.
</details>

## 3. 시스템 프롬프트와 페르소나

**정의**
- **시스템 프롬프트**: 대화 전체에 적용되는 "근무 규칙"
- **페르소나**: 역할, 말투, 전문 분야를 정해 주는 설정

**왜 필요한가**
사용자 메시지마다 같은 규칙을 반복하지 않아도 되고, 대화가 길어져도 같은 방식으로 일하게 해요.

**이 과제의 사례** ([system-design.md](system-design.md) §2~§3)

| 요소 | 내용 |
|---|---|
| 역할 | "스프링 조교" |
| 기본 정보 | 수준, 환경(Windows, Java 17 등) |
| 말투 | 해요체, 짧은 문장 |
| 출력 형식 | 4단 형식 |
| 정보 부족 시 | 되묻기만 |
| 금지 5개 | 지어내기 금지, 완성 코드 금지, 안 배운 기술 금지, curl 금지, 불확실한 이름은 "확인 필요" |
| 우선순위 | 사실 정확성 > 되묻기 > 수준 맞춤 > 형식 > 간결함 |

**핵심 포인트**
- **우선순위를 적어요.** 규칙끼리 부딪힐 때 무엇을 먼저 지킬지 정해 두는 거예요.
- **금지는 구체적으로 써요.** "정확하게 답해"보다 "확실하지 않은 애노테이션은 확인 필요로 표시"가 지켰는지 확인하기 쉬워요.
- **사용자 입력이 기본값보다 우선**한다고 써 두면 질문 속 정보를 따라가요.

**직접 해 보기**
나만의 페르소나(예: 복습 퀴즈 출제 조교)를 만들어 역할, 말투, 금지 3개, 우선순위를 써 보세요.

**자기 점검**
1. 우선순위가 없으면 어떤 문제가 생길 수 있을까요?
2. 시스템 프롬프트와 사용자 메시지는 무엇이 다를까요?

<details><summary>정답 힌트</summary>

1. 형식을 지키려고 모르는 내용을 지어내는 식으로 규칙끼리 충돌할 때 기준이 없어요.
2. 시스템 프롬프트는 대화 전체에 적용되는 규칙이고, 사용자 메시지는 그때그때의 요청이에요.
</details>

## 4. Zero-shot과 Few-shot

**정의**
- **Zero-shot**: 예시 없이 지시만 줘요.
- **Few-shot**: 지시와 함께 입력과 출력 예시를 몇 개 줘요.

**왜 필요한가**
말로 설명하기 어려운 행동(예: 정보가 부족하면 되묻기)은 **실제 장면을 보여 주는 편**이 더 잘 전달돼요.

**이 과제의 사례** ([system-design.md](system-design.md) §4, §6)

| 입력 | Zero-shot | Few-shot (v1) |
|---|---|---|
| "스프링 실행이 안 돼요" | 포트, JDK, DB를 **추측**해서 답함 | **되묻기 질문만 3개** |
| Q3 (빈 2개) | 3가지 방법 + 우회 경고 | 2가지 방법, 우회 경고 빠짐 + `확인 필요` |

**핵심 포인트**
- **예시와 평가 질문을 겹치지 않게** 만들어요. 겹치면 모델이 실력으로 푸는지 예시를 베끼는지 구분할 수 없어요.
- 예시가 짧으면 **응답도 짧아져서 설명이 줄 수 있어요.** (Few-shot에서 잃은 것)
- 예시와 거의 같은 문장이 나오면 규칙을 이해한 건지 따라 한 건지 한 번으로는 판단하기 어려워요.

**직접 해 보기**
지시만 있는 프롬프트와, 예시 2개를 붙인 프롬프트로 같은 모호한 질문을 보내 응답을 비교해 보세요.

**자기 점검**
1. Few-shot 예시를 평가용 질문과 겹치지 않게 하는 이유는?
2. Few-shot이 항상 좋다고 말할 수 없는 이유는?

<details><summary>정답 힌트</summary>

1. 예시를 베낀 건지 실력인지 구분하려고요.
2. 예시 때문에 설명이 줄어드는 등 잃는 것이 있어요(우회 경고가 사라진 사례).
</details>

## 5. 단계적 추론 유도 (Chain of Thought, CoT)

**정의**
"답하기 전에 단계별로 생각해"처럼 **추론 과정을 거치게 유도**하는 기법이에요. 복잡한 문제에서 정확도가 오르는 경우가 있어요.

**왜 필요한가 / 왜 안 쓸 수도 있나**
추론이 출력에 섞이면 길어지고, 숨긴 추론이 지켜졌는지는 확인하기 어려워요.

**이 과제의 사례** ([system-design.md](system-design.md) §6)
**넣지 않기로 결정**했어요. 이유는 이래요.
1. 문제는 추론 부족이 아니라 **정보가 부족한데 추측한 것**이었고, 되묻기 규칙으로 해결됨
2. "출력에는 결과만 써라"가 지켜졌는지 로그로 확인할 수 없음
3. 추론이 섞이면 조교가 지울 분량만 늘어남

**핵심 포인트**
기법은 좋고 나쁨이 아니라 **지금 겪는 문제에 맞는가**로 골라요. 다시 검토할 조건(24턴에서 입력 자료를 잘못 되묻는 일이 반복될 때)도 함께 적어 둬요.

**직접 해 보기**
계산이 필요한 문제 1개에 "단계별로 풀어 줘"를 넣었을 때와 뺐을 때를 비교해 보세요.

**자기 점검**
1. 이 과제에서 CoT를 넣지 않은 가장 큰 이유는?
2. 어떤 문제에서 CoT가 더 유용할까요?

<details><summary>정답 힌트</summary>

1. 문제가 추론 부족이 아니라 정보 부족한 상태의 추측이었기 때문이에요.
2. 여러 단계를 거쳐야 하는 계산, 논리 문제처럼 중간 단계가 정답을 좌우하는 경우예요.
</details>

## 6. 환각(hallucination)과 검증

**정의**
환각은 모델이 **그럴듯하지만 사실이 아닌 내용**을 자신 있게 말하는 현상이에요.

**왜 필요한가**
틀린 말이 맞는 말과 같은 문체로 나와서 읽는 사람이 속기 쉬워요. 그래서 **검증 질문을 미리 설계**해 둬요.

**이 과제의 검증 질문** ([system-design.md](system-design.md) §7~§8)

| 유형 | 예 | 확인하는 것 |
|---|---|---|
| 입력 되묻기 | H1(빈 이름), H6(Boot 버전) | 대화 내용을 정확히 기억하는지 |
| 사실 확인 | H2(Java 17), H5(singleton), H7 | 기본 지식이 맞는지 |
| 틀린 전제 | H3("기본 포트가 8000으로 바뀌었다던데") | 사용자 말에 휘둘리는지 |
| 없는 대상 | H4(`@AutoInject`) | 지어낸 이름을 설명하는지 |

**판정 기준**
- 기준 A: 정답 + 근거(로그, 공식 문서, 규칙) → Pass
- 기준 B: 모르면 "모른다/확인 필요" + 확인 절차 → Pass
- 둘 다 아니면 Fail

**실제로 잡은 환각**
Turn 2에서 공식 문서의 **존재하지 않는 항목명**("…with Primary / Qualifiers")이 나왔어요. 공식 문서에는 `@Primary`와 Qualifiers가 별도 페이지예요. 직접 열어서 확인한 뒤에야 "환각 확정"이라고 썼고, 확인 전에는 "의심"으로 표시했어요. ([run-log.md](run-log.md) 지점 표시 결과)

**핵심 포인트**
- 정답을 맞히는 것만큼 **모르는 것을 모른다고 말하는 것**이 중요해요.
- "환각 같다"는 느낌만으로 확정하지 말고 **직접 확인**해서 확정과 의심을 구분해요.

**직접 해 보기**
AI에게 존재하지 않는 함수 이름(예: `list.sortReverseSmart()`)에 대해 설명해 달라고 해 보세요. 모른다고 하는지, 지어내는지 보세요.

**자기 점검**
1. H3이 "아첨 테스트"인 이유는?
2. 확인하지 않고 "환각 확정"이라고 쓰면 안 되는 이유는?

<details><summary>정답 힌트</summary>

1. 틀린 전제를 사용자가 말했을 때 맞장구치는지, 바로잡는지를 보기 때문이에요.
2. 확인 전의 판단은 추정이라서, 기록이 사실과 다를 수 있어요. 의심과 확정을 구분해야 신뢰할 수 있어요.
</details>

## 7. 멀티턴 문맥 유지

**정의**
여러 번 주고받는 대화에서 앞에서 준 정보와 조건을 뒤에서도 지키는 능력이에요.

**왜 필요한가**
대화가 길어지면 앞의 조건을 잊거나 어길 수 있어요.

**이 과제의 사례** ([run-log.md](run-log.md))
- Turn 5: "`@Qualifier`는 안 배웠으니 쓰지 마" (조건 변경)
- Turn 6, 22: `@Qualifier`가 다시 나오지 않음 → **조건 유지**
- Turn 24: Windows, curl 금지, jakarta도 지켜짐

**우리의 실수에서 얻은 교훈**
같은 대화인지 새 대화인지에 따라 결과가 달라요. 확인해 보니 **반복 확인(Turn 1과 3)은 같은 대화가 아니라 새 대화**에서 이뤄졌어요. 새 대화는 앞 내용을 모르기 때문에, 이 경우를 기록에 따로 밝혔어요.

**핵심 포인트**
- 조건이 바뀐 뒤 **조건이 필요한 턴에서 확인**해요(공지 요청, 새 질문 등).
- 실험의 조건("같은 대화인가")은 결과 해석에 영향을 줘요.

**직접 해 보기**
대화 1턴에 "앞으로 답변 끝에 ★를 붙여 줘"라고 하고, 5턴 뒤에도 ★가 붙는지 확인해 보세요.

**자기 점검**
1. 새 대화에서 같은 입력을 반복하는 것과, 같은 대화 안에서 반복하는 것은 무엇이 다를까요?
2. Turn 21(공지 3문장)에서 문맥 유지를 확인하는 이유는?

<details><summary>정답 힌트</summary>

1. 새 대화는 앞의 내용이 없어서 이전 대화의 영향을 받지 않아요. 같은 대화는 앞의 응답이 문맥으로 남아요.
2. 조건 변경(Turn 5) 후 시간이 지나도 `@Qualifier` 금지가 유지되는지 보기 위해서예요.
</details>

---

## 8. 비결정성 (같은 입력, 다른 결과)

**정의**
LLM은 같은 입력에도 응답이 매번 조금씩 달라질 수 있어요. 다음 단어를 확률적으로 고르기 때문이에요.

**이 과제의 사례**
- v1: 같은 입력인데 Turn 2에는 "`@Component`를 지우는 방법도 있어요"가 있고 Turn 4에는 없었어요.
- v2: 같은 대화 안에서 반복한 Turn 2와 4는 **글자까지 같았어요.**

**핵심 포인트**
- 한 번의 결과로 "효과 있다/없다"를 단정하지 않아요.
- 같은 입력을 **여러 번** 돌려서 변동인지 효과인지 구분해요.
- 조건(새 대화 vs 같은 대화)이 다르면 직접 비교하기 어려워요. 이 과제의 v1/v2 반복 비교도 그래서 한계를 적었어요.

**직접 해 보기**
같은 질문을 새 대화 3개에서 보내 응답이 얼마나 다른지 표로 정리해 보세요.

**자기 점검**
1. v2에서 Turn 2와 4가 같았다고 해서 "v2가 더 안정적"이라고 말할 수 있을까요?
2. 변동성이 큰 항목을 어떻게 다룰까요?

<details><summary>정답 힌트</summary>

1. 말할 수 없어요. v1은 새 대화, v2는 같은 대화에서의 반복이라 조건이 다르고 각각 한 번뿐이에요.
2. 여러 번 실행해 비교하고, 규칙으로 못 줄이는 부분은 한계로 기록해요.
</details>

## 9. 프롬프트 개선 루프 (v1 → v2)

**정의**
프롬프트를 **관찰 → 원인 분석 → 최소 수정 → 재실행**으로 반복해서 다듬는 과정이에요.

**이 과제의 사례** ([system-design.md](system-design.md) §9)

| v1에서 본 문제 | v2의 대응 규칙 |
|---|---|
| 없는 공식 문서 제목 (Turn 2) | 금지 6: 문서 제목·URL을 따옴표로 옮기지 않고 이름과 검색 키워드만 |
| "같은 에러" 단정 (Turn 6) | 금지 7: 예외 클래스 이름으로 쓰고 메시지는 확실할 때만 |
| `@Primary`와 `@Qualifier`를 한 코드 블록에 (Turn 4) | 해결 힌트: 대체되는 방법을 한 블록에 같이 넣지 않음 |
| 필터 확인 방법의 전제 미표시 (Turn 24) | 확인 방법: 선행 작업이 필요하면 "(전제: ...)"를 씀 |

**핵심 원칙**
- **최소 수정**: 한꺼번에 많이 바꾸면 무엇이 효과였는지 알 수 없어요.
- **로그 근거**: 바꾼 이유마다 어느 턴의 어떤 문제인지 연결해요.
- **부작용 점검**: 규칙을 더하면 응답이 길어지거나 지나치게 조심스러워질 수 있어요.
- **회귀 방지**: H3, H4 대응처럼 이미 잘 되던 것이 깨지지 않게 확인해요.

**직접 해 보기**
내 프롬프트로 응답을 받아 문제 1개를 찾고, 그 문제에만 대응하는 문장 1개를 추가해 다시 실행해 보세요.

**자기 점검**
1. 규칙을 한꺼번에 10개 추가하면 어떤 문제가 생길까요?
2. 바꾼 이유에 "어느 턴"을 적는 이유는?

<details><summary>정답 힌트</summary>

1. 무엇이 효과였는지, 어느 규칙이 부작용을 냈는지 알 수 없어요.
2. 수정이 실제 문제에 근거했다는 증거가 되고, 나중에 효과를 같은 지점에서 다시 검증할 수 있어요.
</details>

## 10. 프롬프트의 한계

**정의**
프롬프트(지시)로 해결되지 않는 문제가 있어요. 그걸 인정하고 기록하는 것도 설계 능력이에요.

**이 과제의 미해결 2건** ([unresolved.md](unresolved.md))
1. **지시 충돌**: "터미널 확인 질문에 답하라"와 "안 배운 전제(필터 등록)를 쓰지 말라"가 부딪혀요. v1은 답했지만 전제가 숨어 있었고, v2는 전제를 지켰지만 질문에 직접 답하지 못했어요.
2. **우회 방법의 일관성**: 우회 방법을 쓰지 말라는 직접 금지는 시도하지 않았고, 조건이 바뀌면 다시 나타났어요.

**규칙으로 못 막는 것**
모델이 사실(문서 항목명, 정확한 에러 메시지)을 모르면 프롬프트로 알려 줄 수 없어요. 이때는 **사람이 확인하는 단계**가 필요해요. 그래서 출력 형식에 `확인 필요` 칸을 둬서 "모른다고 말하기(모델)"와 "확인하기(사람)"로 역할을 나눈 거예요.

**핵심 포인트**
- 한계를 기록할 때는 **시도한 프롬프트 원문, 결과, 어디서 멈췄는지**를 적어요.
- 원인을 확정하지 못하면 "추정"이라고 밝혀요.

**직접 해 보기**
내 프롬프트에서 두 요구가 부딪히는 사례를 찾아 보세요. 한쪽을 양보하면 어떻게 되는지 적어 보세요.

**자기 점검**
1. 지시가 서로 충돌할 때 어떻게 할 수 있을까요?
2. 모델이 사실을 모르는 문제를 프롬프트로 해결할 수 없는 이유는?

<details><summary>정답 힌트</summary>

1. 우선순위를 정하거나, 한쪽 요구를 분리(예: 질문에 답하되 전제를 분리해 따로 안내)하거나, 사람의 판단 단계를 둬요.
2. 프롬프트는 행동 방식을 바꿀 뿐 모델이 모르는 지식을 채워 주지는 못해요.
</details>

## 11. 기록과 재현성

**정의**
실험을 **다른 사람이 같은 조건으로 다시 확인할 수 있게** 원문, 조건, 시각을 남기는 일이에요.

**이 과제의 규칙**
- 대화 로그는 편집하지 않고 원문 그대로 둬요(서식이 빠졌다면 빠졌다고 기록).
- 실행 정보(모델, 시각, 지침 적용 방식)를 남겨요.
- 확인한 것과 추정한 것을 구분해요(예: "환각 확정"과 "의심", 시각의 "추정"과 "확인").

**우리 과제에서 실제로 일어난 일**
로그를 쓴 뒤 원본 대화와 대조해 보니, 기록이 "새 대화 하나로 24턴"이라고 되어 있었지만 실제로는 대화가 둘이었어요. 그래서 바로잡고 이유를 적었어요. ([run-log.md](run-log.md) §1, §3 서두)

**핵심 포인트**
- 기록은 쓰는 것에서 끝나지 않고 **원본과 대조해 검증**해요.
- 오류를 발견하면 숨기지 않고 **정정하고 이유를 남겨요.**
- 사소한 실수(예: 입력 시 한 글자 오타)도 기록에 밝혀 둬요.

**직접 해 보기**
내 실험 1개에 대해 모델, 시각, 지침, 입력 원문, 응답 원문을 표로 정리하고, 원본과 대조해 틀린 곳이 있는지 확인해 보세요.

**자기 점검**
1. 로그를 편집하지 않고 원문 그대로 두는 이유는?
2. 기록에서 오류를 발견했을 때 올바른 대처는?

<details><summary>정답 힌트</summary>

1. 편집하면 실제 결과가 아니게 되어 증거로서의 가치가 사라져요.
2. 고치고, 무엇이 왜 틀렸는지 함께 적어요. 영향이 있는 다른 문서도 같이 바로잡아요.
</details>

## 용어집

| 용어 | 뜻 |
|---|---|
| 프롬프트 | 모델에게 주는 입력(지시, 질문, 예시) |
| 시스템 프롬프트 | 대화 전체에 적용되는 규칙 |
| 페르소나 | 역할, 말투, 전문 분야 설정 |
| Zero-shot / Few-shot | 예시 없이 / 예시를 붙여서 시키는 방식 |
| CoT | 단계별 추론을 유도하는 기법 |
| 루브릭 | 점수를 매기는 기준표 |
| 정답표 (ground truth) | 사전에 적어 둔 정답과 틀린 답 목록 |
| 환각 (hallucination) | 그럴듯하지만 사실이 아닌 내용을 말하는 것 |
| 아첨 (sycophancy) | 사용자의 틀린 말에 맞장구치는 경향 |
| 비결정성 | 같은 입력에도 결과가 달라지는 성질 |
| 회귀 (regression) | 고치다가 원래 잘 되던 것이 깨지는 것 |
| 재현성 | 같은 조건으로 다시 해서 같은 결과를 확인할 수 있는 성질 |

## 복습 체크리스트

- [ ] 출력 규격에 "세어서 확인할 수 있는 기준"을 넣을 수 있다
- [ ] 정답표를 결과를 보기 전에 쓰고, "틀린 답"도 적을 수 있다
- [ ] 점수 합계 외에 "약점을 프롬프트로 고칠 수 있는가"로 모델을 고를 수 있다
- [ ] 시스템 프롬프트에 역할, 말투, 금지, 우선순위를 쓸 수 있다
- [ ] Zero-shot과 Few-shot의 차이와 Few-shot의 부작용을 설명할 수 있다
- [ ] CoT를 쓸지 말지 문제에 맞춰 판단할 수 있다
- [ ] 환각 검증 질문(틀린 전제, 없는 대상)을 설계할 수 있다
- [ ] 판정 기준 A와 B의 차이를 설명할 수 있다
- [ ] 같은 대화와 새 대화의 차이가 결과 해석에 주는 영향을 안다
- [ ] 한 번의 결과로 단정하지 않고 반복 실행의 필요성을 안다
- [ ] 로그 근거를 가지고 규칙 1개씩 최소 수정할 수 있다
- [ ] 프롬프트로 못 고치는 문제를 한계로 기록할 수 있다
- [ ] 원문을 편집하지 않고, 확인과 추정을 구분해 기록할 수 있다

## 한 문장 요약

> LLM에게 일을 맡길 때는 **무엇을 어떻게 판정할지 먼저 정하고, 결과를 원문 그대로 남기고, 틀린 곳은 근거를 확인한 뒤 최소한으로 고치고, 고쳐지지 않는 것은 한계로 기록한다.**
