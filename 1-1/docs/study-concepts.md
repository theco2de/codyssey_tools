## 이 과제와 현업의 차이

이 과제는 개념 학습을 위한 소규모 실습이다. 현업과의 규모 차이는 아래와 같다.

| 항목 | 이 과제 | 현업에서 흔히 필요한 수준 |
|---|---|---|
| 평가 규모 | 질문 3건, 검증 질문 7건, 조건마다 1회 실행 | 수십~수천 건, 반복 실행 |
| 평가자 | 1명 | 복수 평가자 또는 자동 채점 + 사람 검수 |
| 실행 방식 | 화면에서 복사해 붙임 | 스크립트나 하네스를 통한 자동 실행 |
| 프롬프트 관리 | 문서 안의 v1, v2 | 저장소, 배포 단계, 변경 리뷰 |
| 모델 설정 | 화면 기본값 | 모델 ID와 파라미터의 기록과 고정 |
| 입력 | 가상 수강생 질문 | 실제 사용자 입력(신뢰할 수 없음) |
| 데이터 | 가상 예시 | 개인정보와 영업비밀 규정 |
| 비용·지연 | 고려하지 않음 | 건당 비용과 응답 시간이 설계 조건 |

이 차이는 실패가 아니라 규모와 목적의 차이이다.

## 1. 과업 정의와 출력 규격

> LLM에게 일을 맡기기 전에 입력의 종류와 출력의 형태를 먼저 정한다.

### 개념

기준 없이 "잘 답하라"고만 지시하면 응답의 길이, 구조, 깊이가 매번 달라져서 품질을 판정할 수 없다.
일을 맡기기 전에 아래 일곱 가지를 정한다.

| 요소 | 질문 | 이 과제의 답 |
|---|---|---|
| 목적 | 수행하는 이유 | 반복되는 질문 답변의 시간과 편차 감소 |
| 사용자 | 사용 주체 | 직접 사용자는 조교, 최종 독자는 수강생 |
| 입력 | 받는 것 | 질문, 에러 로그, 환경, 진도 |
| 출력 | 내는 것 | 4단 답변 초안 |
| 성공 기준 | 성공 판정 방법 | 기준 5개와 정답표 |
| 비목표 | 하지 않는 일 | 완성 코드 제공, 안 배운 기술을 해결책으로 사용 |
| 예외 | 입력이 부족할 때의 처리 | 되묻기 질문만 최대 3개 |

#### 출력 규격의 세 층

1. 구조: 항목의 유무와 순서
2. 분량: 문장 수, 단계 수, 줄 수
3. 의미: 내용의 정확성과 유용성

구조와 분량은 세어서 확인할 수 있지만 의미는 정답표나 사람의 판단이 필요하다.

#### 형식과 정확성의 분리

형식을 지켰다고 내용이 정확한 것은 아니다. 이 과제의 Zero-shot 응답도 4단 형식은 지켰지만 모호한 입력에는 추측으로 답했다.

#### 입력과 예외의 규격화

로그가 없을 때 "없음"으로 적게 하는 것처럼 빈칸의 표현 방식을 정해야 모델이 빈칸을 지어서 채우지 않는다.
"정보가 충분한가"를 먼저 판단해서 답변과 되묻기로 나누는 것은 하나의 의사결정이다. 이 판단이 틀리면 이후의 품질은 의미가 없다.

### 이 과제에서는

- 출력: 원인 추정(1~2문장), 확인 방법(최대 3단계), 해결 힌트(코드 3줄 이하), 함께 볼 개념(1개) ([system-design.md](system-design.md) §1)
- 정보 부족 시: 4단 대신 되묻기 질문만 최대 3개
- 개수 제한의 확인 방식: 사람이 눈으로 세어서 확인
- 위반 사례: Zero-shot의 "스프링 실행이 안 돼요" 응답은 원인이 3문장으로 "1~2문장" 제한 초과

### 현업에서는

#### 과업 문서

- 기재 항목: 목적, 사용자, 입력과 출력 계약, 비목표, 담당자, 응답 시간과 비용 목표, 위험 등급
- 용도: "이 시스템이 하기로 한 일인가"를 따질 때의 기준

#### 컴퓨터가 읽는 출력

출력이 다른 시스템으로 전달되면 사람이 읽는 문장이 아니라 스키마가 있는 구조(JSON 등)가 필요하다.

- 필수 필드, 허용 값 목록, 길이 제한을 스키마로 정의
- 응답의 스키마 만족 여부를 코드로 검증
- 실패 시 정해진 횟수만 재시도하고, 이후 대체 응답이나 사람 연결로 전환
- 구조화 출력과 도구 호출 기능의 지원 방식은 제공사마다 다르므로 공식 문서 확인 필요

#### 형식 검증과 의미 검증의 분리

- 구조와 분량: 코드가 모든 요청에서 검사 (저렴하고 빠름)
- 의미: 평가 데이터셋과 표본 검수가 담당
- 이 과제에서 사람이 문장 수를 세던 작업이 코드로 이동

#### 앞단의 분기 처리

"정보가 충분한가"를 판단하는 단계를 본 답변 앞에 별도로 두는 설계가 흔하다(분류기나 작은 모델 사용).
이 과제의 되묻기 분기가 그 단순한 형태이며, 이 판단의 정확도도 별도 지표로 측정한다.

#### 규격의 버전 관리

필드 하나의 변경도 이를 받는 시스템을 깨뜨릴 수 있다. 스키마를 버전으로 관리하고 변경을 공지한다.

#### 사용자 계층의 구분

직접 사용자(조교)와 최종 독자(수강생)가 다르면 책임 소재가 달라진다.
"초안이며 담당자가 검토한다"는 고지와 검토 절차를 설계에 포함한다.

#### 흔한 실패

- 성공 기준의 부재로 "좋아졌다, 나빠졌다"를 말로만 다툼
- 예외 경로의 부재로 이상한 입력에 이상한 응답이 그대로 출력됨
- 규격이 문서에만 있고 코드가 검사하지 않아 시간이 지나며 어긋남

### 이 과제와 현업의 차이

3개 질문에서는 사람이 개수를 세는 방식이 가능했지만 규모가 커지면 놓치는 위반이 늘어난다.
사람의 최종 검토는 현업에서도 중요한 안전장치이나, 형식 검사까지 사람이 맡으면 검토자의 시간이 병목이 된다.

## 2. 모델 평가: 루브릭과 정답표

> 모델은 인상이 아니라 결과를 보기 전에 정한 기준으로 비교한다.

### 개념

평가는 네 부분으로 구성된다.

1. 데이터: 평가에 사용하는 입력
2. 기준: 측정 대상
3. 채점자: 점수를 부여하는 주체
4. 집계: 점수를 합치는 방법

#### 루브릭과 정답표

- 루브릭: 점수를 매기는 기준표
- 정답표(ground truth): 맞는 답과 틀린 답으로 볼 것을 결과 확인 전에 적어 둔 표

결과를 본 뒤에 기준을 정하면 선호하는 쪽으로 기울기 쉬우므로 정답표는 결과 확인 전에 작성한다.
틀린 답까지 적어 두면 "그럴듯하지만 틀린 답"을 놓치지 않는다.

#### 루브릭 설계 원칙

- 기준 간 중복 배제: 서로 다른 실패를 잡는 기준으로 구성
- 점수별 설명(앵커) 작성: 5점과 1점만 설명하면 2~4점은 채점자 판단에 의존
- 가중치 결정: 동일 비중이면 사실 오류와 어투 차이가 같은 무게로 합산

#### 신뢰도와 타당도

- 신뢰도: 채점자나 날짜가 바뀌어도 같은 점수가 나오는 정도
- 타당도: 측정하려는 것을 실제로 측정하는 정도 (형식 점수가 높아도 도움이 되는 답이 아닐 수 있음)

#### 공정한 비교

같은 프롬프트, 새 대화, 같은 시점, 지침 비움처럼 변수를 통제해야 한다. 요금제나 설정이 다르면 비교가 흐려진다.

#### 평균의 함정

평균은 치명적 오류를 희석한다. 사실 정확성에서 크게 틀려도 나머지 기준이 만점이면 합계는 높다.
이를 막기 위해 "치명 오류 0건"과 같은, 평균과 별개의 통과 조건(게이트)을 둔다.

### 이 과제에서는

([model-comparison.md](model-comparison.md) §4~§8)

- 기준 5개: 형식 준수, 사실 정확성, 수준 맞춤, 힌트 우선, 환경 반영
- 정답표: "틀린 답으로 볼 것"(`javax.servlet-api` 의존성 추가, `required=false` 등) 포함
- 합계: GPT 22, Gemini 25, Claude 24
- 모델 선정 기준: 점수 합계가 아니라 "남은 약점을 프롬프트로 고칠 수 있는가"
  - 고칠 수 있다고 본 약점: 문장 수 초과, 분량, 어투
  - 고치기 어렵다고 본 약점: 명령어 세부 오류(`findstr 8080`에 콜론 없음) 같은 정확성 문제
- 비교 조건의 한계: 모델별 요금제 상이 (무료 ChatGPT·Gemini, Pro Claude)

### 현업에서는

#### 평가 데이터셋의 자산화

- 출처: 실제 사용 로그 샘플, 도메인 전문가가 만든 사례, 사람이 검수한 합성 데이터
- 구성: 대표 사례와 경계 사례(틀린 전제, 없는 대상, 모호한 입력, 긴 입력, 적대적 입력)
- 분할: 개발용 데이터와 홀드아웃(마지막 확인에만 사용하는 데이터) 분리. 같은 데이터로 계속 수정하면 그 데이터에만 맞는 프롬프트가 됨
- 버전 관리: 데이터셋도 코드처럼 변경 이력 관리

#### 지표

| 지표 | 예 |
|---|---|
| 정확도 | 정답표 대조 통과율 |
| 형식 준수율 | 스키마 검증 통과율 |
| 되묻기 적절성 | 정보 부족 시 되묻는 비율, 정보 충분 시 불필요하게 되묻는 비율 |
| 치명 오류율 | 사실 오류, 금지 위반, 민감정보 노출 건수 (통과 조건으로 사용) |
| 비용 | 요청당 토큰과 금액 |
| 지연 | 응답 시간의 중앙값과 느린 쪽 꼬리(p95 등) |
| 안정성 | 같은 입력 반복 시 일치율 |

#### 채점 방식

| 방식 | 장점 | 한계 |
|---|---|---|
| 규칙 기반(코드) | 빠르고 저렴하고 일관됨 | 의미 판단 불가 |
| LLM 채점자 | 의미를 어느 정도 판단, 대량 처리 가능 | 편향이 알려져 있음 (먼저 나온 답, 긴 답, 자기 모델의 답 선호) |
| 사람 검수 | 가장 신뢰할 만함 | 느리고 비싸고 사람마다 다름 |

- LLM 채점자의 편향 완화: 순서 섞기, 루브릭 명시, 사람 표본과의 일치도 확인
- 사람 검수: 채점자 간 일치도(Cohen's kappa 등)를 측정해 기준의 모호성 점검

#### 표본 크기

표본이 작으면 통과율의 불확실성이 크다. 윌슨 구간(이항 비율의 신뢰구간)으로 계산하면 아래와 같다.

- 10건 중 9건 통과(90%): 95% 신뢰구간 약 60%~98%
- 7건 중 7건 통과(100%): 95% 신뢰구간의 하한 약 65%

전부 통과했다는 사실이 충분한 신뢰를 뜻하지는 않는다. 평가 데이터를 늘리고 반복 실행하는 이유이다.

#### 모델 선정 절차

후보 선정 → 오프라인 평가 → 소규모 파일럿 → 운영 모니터링의 순서가 일반적이다. 정확도 외에 아래 항목을 함께 검토한다.

- 비용, 지연, 호출 한도
- 데이터 취급 조건(저장, 학습 사용 여부, 보존 기간, 처리 지역)과 보안 인증
- 모델 종료 정책과 지원 기간

한 모델만 선택하지 않고 난이도에 따라 분담하는 방식도 있다(쉬운 질문은 작은 모델, 어려운 질문은 큰 모델).

#### 재평가

새 모델 출시나 사용 중인 모델의 종료 시점마다 같은 평가를 다시 실행해 결과가 악화되지 않았는지 확인한다.
Anthropic의 평가 가이드는 성공 기준을 구체적이고 측정 가능하게 정의하고 실제 과업을 닮은 평가를 만들 것을 안내한다.

### 이 과제와 현업의 차이

평가자 1명, 조건마다 1회 실행이므로 25, 24, 22점의 차이를 의미 있는 차이로 보기 어렵다.
모델 선정의 근거("프롬프트로 고칠 수 있다")도 실험이 아니라 판단이었다. 현업에서는 이 가설을 먼저 평가로 확인한다.

## 3. 시스템 프롬프트와 페르소나

> 시스템 프롬프트는 대화 전체에 적용되는 근무 규칙이고, 사용자 메시지는 그때그때의 요청이다.

### 개념

#### 프롬프트의 세 층

- 시스템 프롬프트: 바뀌지 않는 규칙(역할, 말투, 형식, 금지, 우선순위)
- 사용자 입력: 그때그때 달라지는 것(질문, 로그, 환경)
- 예시: 행동을 보여 주는 입력과 출력의 쌍

안정적인 규칙은 시스템에, 요청마다 달라지는 데이터는 사용자 입력에 둔다.
데이터를 시스템에 고정하면 바꿀 때마다 프롬프트를 새로 배포해야 한다.

#### 좋은 지침의 조건

- 구체성: "친절하게"보다 "해요체, 짧은 문장, 수강생을 탓하지 않음"
- 확인 가능성: 지켰는지 눈으로 판단할 수 있을 것
- 예외 처리: 규칙이 맞지 않는 상황의 행동까지 명시 (예: 정보 부족 시 되묻기만)
- 우선순위: 규칙이 충돌할 때의 기준
- 금지와 대안의 병기: "지어내지 말 것"보다 "확실하지 않으면 확인 필요로 표시"가 행동을 안내

#### 길이와 충돌

규칙이 늘어날수록 모든 규칙을 지키기 어렵고 규칙 간 모순 가능성도 커진다. 필요한 규칙만 두는 편이 안정적이다.

#### 페르소나의 효과와 한계

말투, 관점, 설명 깊이에는 효과가 있으나 사실 정확성을 보장하지는 않는다.
"전문가처럼 답하라"고 지시해도 모르는 것은 여전히 모른다.

### 이 과제에서는

([system-design.md](system-design.md) §2~§3)

| 요소 | 내용 |
|---|---|
| 역할 | 수강생 질문에 답변 초안을 쓰는 조교 보조 (스프링 조교) |
| 기본 정보 | 수준(JPA, Security 미학습), 환경(Windows, IntelliJ, Boot 3.x, Java 17) |
| 말투 | 해요체, 짧은 문장 |
| 정보 부족 시 | 되묻기 질문만 |
| 금지 5개 | 지어내기, 완성 코드, 안 배운 기술, curl, 불확실한 이름은 "확인 필요" |
| 우선순위 | 사실 정확성 > 되묻기 > 수준 맞춤 > 형식 > 간결함 |

- 우선순위의 역할: 규칙 충돌 시 기준 제공 (형식을 지키려고 모르는 것을 지어내면 안 됨)
- "질문에 다른 정보가 있으면 그걸 우선" 규정: 입력에 담긴 환경 정보의 수용
- 지침이 없을 때의 어투: Zero-shot에서 Q3는 해요체, 모호 입력은 합니다체로 불일치

### 현업에서는

#### 프롬프트의 생애주기

작성 → 리뷰 → 평가 → 배포 → 모니터링 → 개선 → 폐기. 코드와 같은 절차를 따른다.

- 저장소에서 버전 관리, 변경은 리뷰와 승인
- 개발, 검증, 운영 환경에 단계적 배포
- 어느 버전이 언제 어느 사용자에게 나갔는지 추적, 문제 발생 시 이전 버전으로 복귀
- 관리 방식: 프롬프트 관리 도구 또는 일반 저장소와 설정 파일

#### 컨텍스트 조립

모델에 실제로 전달되는 입력은 프롬프트 하나가 아니라 여러 조각을 합친 결과이다.

- 시스템 규칙
- 사용자 프로필(수준, 진도)
- 검색해 온 근거 문서
- 대화 이력
- 현재 질문

입력 길이에는 한도가 있으므로 조각별로 토큰 예산을 배분한다. 근거 문서가 길면 대화 이력을 줄이는 방식이다.
이 과제의 입력 템플릿([system-design.md](system-design.md) §5-2)이 이 조립의 가장 작은 형태이다.

#### 보안 관점

- 시스템 프롬프트는 사용자가 알아낼 수 있다고 가정하며, 키, 내부 정책, 민감한 비즈니스 규칙을 넣지 않음
- OWASP LLM 상위 10대 위험 2025판의 "System Prompt Leakage"(LLM07)
- 사용자 입력은 지시가 아니라 데이터로 취급하고 입력 속 지시를 따르지 않도록 설계 (10번 참조)

#### 도구를 사용하는 경우

모델이 외부 도구(검색, 계산, 사내 시스템)를 호출하면 도구 설명도 프롬프트의 일부이다. 설명이 모호하면 잘못된 도구를 호출한다.

#### 조직 운영

- 프롬프트별 소유자 지정, 여러 팀의 동시 수정 방지
- 변경 요청에 문제, 가설, 변경 내용, 평가 결과 기재
- 브랜드 톤, 금칙어, 법적 고지 문구의 마케팅·법무 검토
- 다국어 서비스에서는 언어별 규칙 준수 여부를 별도 평가

### 이 과제와 현업의 차이

claude.ai 화면의 프로젝트 지침에 붙여 넣는 방식이어서 배포 단위와 버전 추적이 없었다.
어느 대화가 어느 지침 버전으로 실행됐는지는 사람이 기록으로 남겼다.

## 4. Zero-shot과 Few-shot

> 말로 설명하기 어려운 행동은 예시로 보여 주는 편이 잘 전달되지만, 예시가 응답을 끌고 가는 부작용이 있다.

### 개념

- Zero-shot: 예시 없이 지시만 제공
- Few-shot: 지시와 함께 입력과 출력의 예시를 몇 개 제공

모델의 가중치는 바뀌지 않는다. 프롬프트 안의 예시를 보고 해당 대화에서만 행동을 맞추며 대화가 끝나면 사라진다. 이를 맥락 속 학습(in-context learning)이라고 한다.

#### 예시의 기능

1. 형식 시범: 4단 구조의 실제 모습
2. 경계 사례 시범: 정보 부족 시 되묻기, 범위 밖 질문처럼 규칙으로 설명하기 어려운 장면
3. 말투 시범: 해요체의 구체적 느낌

#### 좋은 예시의 조건

- 대표성과 다양성: 비슷한 예시만 있으면 그쪽으로 쏠림
- 경계 사례 포함
- 규칙과의 일관성: 예시가 규칙을 어기면 모델은 예시를 따름
- 예시 수에 비례하는 비용

#### 부작용

- 스타일 고착: 예시가 짧으면 응답도 짧아짐
- 표면 모방: 예시의 문장을 거의 그대로 가져옴
- 예시 편향: 예시에 자주 나온 해법을 과용
- 내용 누락: 예시에 없던 유형의 설명이 사라질 수 있음

### 이 과제에서는

([system-design.md](system-design.md) §4, §6)

| 입력 | Zero-shot | Few-shot (v1) |
|---|---|---|
| "스프링 실행이 안 돼요" | 포트, JDK, DB를 추측해서 답함 | 되묻기 질문만 3개 |
| Q3 (빈 2개) | 방법 3가지와 우회 경고 | 방법 2가지, 우회 경고 없음, 확인 필요 추가 |

- 예시 4건: 404, 415, 모호한 입력, 범위 밖 기술. 비교용 질문과 겹치지 않게 구성 (겹치면 모델이 실력으로 푸는지 예시를 베끼는지 구분 불가)
- 효과: "정보가 부족하면 되물을 것"을 글로 적는 것보다 되묻는 장면을 보여 주는 편이 효과적
- 부작용: 우회 경고 소실, 모호한 입력에 대한 되묻기 질문 일부가 예시와 거의 같은 문장

### 현업에서는

#### 정적 예시와 동적 예시

- 정적: 항상 같은 예시 사용. 단순하고 예측하기 쉬움
- 동적: 입력과 비슷한 예시를 검색해서 사용. 사례가 많을 때 유리하나 검색 시스템과 예시 저장소의 운영이 필요

#### 예시 저장소 관리

- 예시별 품질 심사, 중복 제거, 오래된 예시 정리
- 정책 변경 시 예시도 함께 변경 (예시가 최신 규칙과 어긋나면 모델은 예시를 따름)

#### 평가 데이터와의 분리

예시 풀과 평가 데이터가 겹치면 점수가 부풀려진다(데이터 누수). 이 분리를 자동으로 검사하는 팀도 있다.

#### 비용과 지연

예시는 호출할 때마다 전송되는 토큰이다. 예시 4건이면 모든 호출에 해당 입력 비용이 든다.
제공사가 프롬프트 캐싱 같은 기능을 지원하면 같은 앞부분을 재사용해 줄일 수 있다. 지원 여부와 방식은 제공사마다 다르다.

#### 대안과의 구분

규칙, 예시, 검색, 미세 조정은 해결하는 문제가 다르다.

| 방법 | 적합한 문제 | 한계 |
|---|---|---|
| 규칙(지침) | 명확히 적을 수 있는 행동 | 길어지면 충돌하거나 어김 |
| Few-shot | 형식, 말투, 경계 사례 시범 | 토큰 비용, 스타일 고착 |
| 검색(RAG) | 모델이 모르는 지식의 공급 | 검색 품질에 의존 |
| 미세 조정 | 대량의 일관된 행동과 스타일 | 데이터 확보, 비용, 유지 보수, 모델 교체 시 재작업 |

지식을 예시로 가르치려는 시도는 잘못된 선택이다. 지식은 검색으로, 행동은 규칙과 예시로 다룬다.

#### 예시의 데이터 문제

실제 고객 질문을 예시로 쓰면 개인정보, 영업비밀, 저작권 문제가 생길 수 있어 마스킹하거나 가공한다.

#### 예시 변경 시 재평가

응답 스타일이 바뀌고 잘 되던 항목이 깨질 수 있으므로 예시를 바꿀 때마다 평가를 다시 실행한다.

### 이 과제와 현업의 차이

예시를 바꾼 뒤 평가를 반복하지는 않았고, 부작용(우회 경고 소실)은 눈으로 비교해서 찾았다.
현업에서는 이 비교가 평가 데이터셋 위에서 자동으로 수행된다.

## 5. 단계적 추론 유도 (CoT)

> 기법의 선택 기준은 우열이 아니라 해결하려는 문제와의 적합성이다.

### 개념

모델이 최종 답을 내기 전에 중간 추론을 글로 쓰게 하면 그 내용이 이어지는 답의 근거가 되어 여러 단계가 필요한 문제의 정확도가 오르는 경우가 있다.

#### 효과가 큰 경우와 작은 경우

- 큰 경우: 여러 단계를 거치는 계산, 논리, 조건 분기가 많은 판단
- 작은 경우: 단순 사실 회상, 형식 변환, 정해진 틀 채우기

#### 구현 방식

1. 프롬프트로 유도 ("단계별로 생각하라")
2. 모델의 추론 모드 사용 (생각 과정을 따로 생성하는 기능. 지원 여부와 설정은 모델마다 다름)
3. 두 번 호출 (1단계 분석, 2단계 분석 기반 답변)

#### 위험

- 길어짐: 비용과 지연 증가. 추론 토큰도 비용
- 충실성 문제: 추론 텍스트가 실제로 답을 만든 과정을 그대로 설명한다는 보장이 없다는 지적이 있으며, 이를 근거로 그대로 신뢰하지 않는 팀이 많음
- 노출 문제: 사용자에게 추론을 보여 주면 틀린 중간 단계가 오해를 만들거나 내부 정보가 섞일 수 있음

### 이 과제에서는

([system-design.md](system-design.md) §6)

결정: 도입하지 않음. 이유는 세 가지이다.

1. 문제는 추론 부족이 아니라 정보가 부족한데 추측한 것이었고, 되묻기 규칙으로 해결됨
2. "추론은 속으로 하고 출력에는 결과만 쓸 것"이 지켜졌는지 로그로 확인 불가
3. 추론이 섞이면 조교가 지워야 할 분량만 증가

재검토 조건: 24턴 시나리오에서 입력 자료를 잘못 되묻는 일이 반복되면 도입. 실제로는 해당 사례가 나타나지 않았다.

### 현업에서는

#### 비용과 정확도의 교환

추론을 켜면 정확도가 오를 수 있으나 토큰과 지연이 늘어난다.
같은 평가 데이터셋에서 켰을 때와 껐을 때를 비교해 정확도 이득이 비용을 정당화하는지 판단한다.

#### 문제 유형별 분리

모든 요청에 추론을 켜지 않고 어려운 요청에만 켜는 방식이 흔하다.
이 과제에 적용하면 단순한 개념 질문은 끄고, 원인이 여러 개 얽힌 에러 로그에만 켜는 구성이다.

#### 추론과 최종 답의 분리

- 최종 답만 구조화된 필드로 추출해 사용자에게 전달
- 추론 텍스트는 내부 로그로만 보관하는 경우도 있음
- 추론 텍스트에도 민감정보가 포함될 수 있으므로 보존 정책의 대상

#### 추론 노출 정책

사용자에게 보여 줄지 숨길지는 제품 결정이다. 과정을 보는 것이 가치인 교육 제품에서는 노출하고, 업무 보조에서는 숨기는 경우가 많다.

#### 추론 대신 도구

계산이나 사실 확인은 추론에 맡기기보다 계산기, 코드 실행, 검색 같은 도구를 호출하는 편이 검증하기 쉽고 정확하다.
이 과제에 적용하면 해결 힌트의 코드 조각을 추론으로 점검하는 대신 실제로 컴파일해 보는 방식이다.

#### 평가 설계

- 켜기와 끄기의 비교(A/B)
- 문제 유형별 분해 (이득이 나는 지점 파악)
- 비용과 지연 변화의 병기

### 이 과제와 현업의 차이

이 과제는 CoT 도입 여부를 실험이 아니라 문제 유형 분석(추론 부족이 아닌 정보 부족)으로 결정했다.
방향은 합리적이었으나 현업에서는 켜고 끈 결과를 수치로 비교한다.

## 6. 환각과 검증

> 모델은 모르는 것을 그럴듯하게 지어낼 수 있으며, 정답을 아는 것만큼 모른다고 말하는 것이 중요하다.

### 개념

환각은 모델이 그럴듯하지만 사실이 아닌 내용을 자신 있게 말하는 현상이다.
틀린 말이 맞는 말과 같은 문체로 나오므로 읽는 사람이 속기 쉽다.

#### 발생 원인

일반적으로 알려진 설명은 다음과 같다.

- 모델은 다음에 올 그럴듯한 말을 이어 쓰므로 모르는 것도 자연스러운 문장으로 채울 수 있음
- 학습한 지식의 한계와 시점
- 사용자의 말을 전제로 받아들이는 경향(아첨)으로 틀린 전제도 바로잡지 않고 따라감
- 긴 입력에서 앞의 내용을 다르게 옮기는 경우

#### 환각의 유형

| 유형 | 예 |
|---|---|
| 사실 오류 | 기본 포트를 8000이라고 답함 |
| 지어낸 대상 | 없는 애노테이션, 없는 문서 제목, 없는 인용 |
| 입력 왜곡 | 붙여 넣은 로그의 빈 이름을 다르게 답함 |
| 문맥 불일치 | 앞에서 준 조건과 다르게 답함 |
| 과신 | 불확실한 내용을 단정함 |

#### 검증 설계

잡으려는 틀림의 유형을 먼저 정하고, 유형마다 정답 판정과 근거 요구를 정한다.

#### 정직성

좋은 응답은 정답을 맞히는 것뿐 아니라 모를 때 모른다고 말하는 것이다.
이 과제의 판정 기준 B("모른다, 확인 필요"라고 밝히고 확인 절차를 제안)가 이 뜻이다.

#### 확정과 의심의 구분

"환각 같다"는 인상만으로 확정하지 않고, 1차 자료(공식 문서, 소스 코드)로 확인한 뒤에 확정한다.

### 이 과제에서는

([system-design.md](system-design.md) §7~§8)

| 유형 | 검증 질문 | 응답 |
|---|---|---|
| 입력 되묻기 | H1(빈 이름), H6(Boot 버전) | 정확히 답함 |
| 사실 확인 | H2(Java 17), H5(singleton), H7(`@Controller` + `@ResponseBody`) | 정답 |
| 틀린 전제 | H3("8000으로 바뀌었다던데") | "아니요, 기본 포트는 8080"으로 바로잡음 |
| 없는 대상 | H4(`@AutoInject`) | "표준에는 없는 걸로 알지만 단정할 수는 없다"와 확인 절차 3가지 |

- 판정 기준: A는 정답과 근거를 함께 제시, B는 모를 때 모른다고 밝히고 확인 절차를 제안. 일곱 개 모두 Pass이며 H5와 H7은 출처 언급이 없어 경계로 표시
- v1 Turn 2의 환각: 공식 문서에 없는 항목명("…with Primary / Qualifiers"). 공식 문서에는 `@Primary`와 Qualifiers가 별도 페이지. 문서를 직접 열어 확인한 뒤 환각으로 확정했고, 확인 전에는 의심으로 표시
- Turn 6의 "같은 에러가 다시 난다": 스프링 소스 확인 결과 예외 종류는 같으나 메시지가 다르므로 경미한 부정확으로 표시

### 현업에서는

#### 환각 완화의 층 구조

| 층 | 방법 | 이 과제의 대응 |
|---|---|---|
| 1. 근거 공급 | 검색(RAG)으로 관련 문서를 찾아 근거로 제공하고 인용하게 함 | 없음 |
| 2. 출력 제약 | 스키마와 허용 값 목록으로 지어낼 여지 축소 | 4단 형식 |
| 3. 생성 후 검증 | 인용 출처 존재 확인, 코드 컴파일, 사실 확인 | 사람이 직접 확인 |
| 4. 불확실성 처리 | 모른다는 응답 허용, 확신이 낮으면 사람에게 이관 | 확인 필요 칸 |
| 5. 사람 검토 | 최종 확인 | 조교 |

#### RAG의 구성

1. 문서를 조각으로 분할(청킹)
2. 조각을 색인(임베딩)
3. 질문에 맞는 조각을 검색 (필요하면 재순위화)
4. 검색한 조각을 근거로 제공하고 인용과 함께 답변

검색이 틀리면 근거도 틀리므로 검색 품질도 별도로 평가한다.

#### 이 과제에 적용한다면

- Spring 공식 문서를 색인해 근거로 삼고 답변에 문서 링크를 첨부
- 답변이 인용한 문서 제목과 URL의 실제 존재 여부를 자동 조회, 없으면 재생성하거나 사람에게 이관 (v1 Turn 2의 없는 문서 제목이 이 검사로 잡히는 유형)
- 코드 조각은 샌드박스에서 컴파일과 테스트 실행
- 에러 메시지처럼 정확한 문구가 필요한 내용은 모델의 기억이 아니라 소스나 로그에서 가져와 사용

#### 측정

- 환각률: 응답 중 사실 오류가 포함된 비율. 오류를 사소함, 중요, 치명으로 등급화
- 운영 응답의 일부를 사람이 검수해 환각률 추정 (신뢰구간 병기)
- 틀린 전제와 없는 대상을 넣은 검증 질문을 평가 데이터에 지속 추가 (레드팀)

#### 운영 루프

사용자가 "틀렸다"고 신고할 수 있게 하고, 신고된 사례를 평가 데이터에 편입한다. 같은 환각의 반복 여부를 추적한다.

#### 허용 기준과 책임

- 용도별 허용 오류 수준을 먼저 결정 (조교가 검토하는 초안은 넓게, 사용자에게 바로 나가는 답변은 좁게)
- 사용자 대면 서비스에서는 "AI가 만든 답변이며 검토가 필요하다"는 고지와 최종 판단은 사람이 한다는 절차를 설계에 포함
- 책임 범위는 법무와 협의

#### 보안 목록과의 관계

잘못된 정보는 보안 위험 목록에도 포함된다. OWASP LLM 상위 10대의 Misinformation은 2025판 LLM09, 2026판 LLM07이다.

### 이 과제와 현업의 차이

사람이 최종 검토하는 구조여서 환각의 위험이 낮았다. 환각의 확인도 사람이 공식 문서를 열어 수행했으며, 규모가 커지면 이 확인을 자동화해야 한다.
이 과제에는 1~3층(근거 공급, 출력 제약의 강한 형태, 생성 후 검증)이 없었고 4~5층(불확실성 표시, 사람 검토)에 의존했다.

## 7. 멀티턴 문맥 유지

> 대화가 길어져도 앞에서 준 조건이 유지되어야 하며, 같은 대화인지 새 대화인지가 결과 해석을 바꾼다.

### 개념

#### 모델의 상태 부재

대화처럼 보이는 것은 매 호출마다 지금까지의 대화 이력을 다시 전송하기 때문이다.
모델이 기억하는 것은 입력에 포함된 내용뿐이다. 따라서 새 대화는 앞의 내용을 모르며, 이력이 길수록 매 턴의 비용이 늘어난다.

#### 컨텍스트 윈도우의 한계

한 번에 볼 수 있는 입력 길이에는 한도가 있다. 길어지면 오래된 부분을 잘라 내거나 요약해야 하고, 한도 안이라도 앞부분의 영향이 약해지거나 혼동이 생길 수 있다.

#### 조건 유지가 깨지는 방식

- 앞의 규칙을 잊음
- 새 지시와 기존 규칙이 충돌할 때 한쪽이 무시됨
- 대화 중 사용자가 바꾼 조건이 시스템 규칙에 눌림

#### 같은 대화와 새 대화

같은 입력이라도 이력이 있으면 응답이 달라질 수 있다. 실험에서는 어느 쪽인지가 결과 해석에 영향을 준다.

### 이 과제에서는

([run-log.md](run-log.md))

- Turn 5: "`@Qualifier`는 안 배웠으니 쓰지 말 것"으로 조건 변경
- Turn 6, 22(공지 3문장): `@Qualifier`가 나오지 않아 조건 유지
- Turn 24: Windows 조건, curl 금지, jakarta 준수
- 반복 확인(Turn 2와 4): 새 대화에서 같은 입력을 다시 보낸 방식. 같은 대화 안에서의 반복과 조건이 달라 이 점을 기록에 명시

### 현업에서는

#### 애플리케이션이 담당하는 상태 관리

모델의 기억에 의존하지 않고 앱이 상태를 설계한다.

- 세션 저장소에 대화 이력 보관, 길어지면 오래된 부분을 요약하거나 잘라서 컨텍스트에 맞춤
- 중요한 사실과 조건(예: 이 반은 `@Qualifier`를 안 배움, 환경은 Windows 11)은 이력에 묻어 두지 않고 별도 필드로 저장해 매 호출에 다시 주입. 이력이 요약되어 사라져도 조건은 유지
- 사용자별 장기 메모리(선호, 진도)는 동의, 열람, 삭제 요청에 대응해야 하는 개인정보

#### 컨텍스트 예산

시스템 규칙, 이력, 검색 결과, 출력 길이가 한도를 나눠 쓴다.
이력이 길수록 매 턴 비용이 늘어나므로 요약 시점과 방법은 비용과 품질의 균형 문제이다.

#### 멀티턴 회귀 테스트의 자동화

대화 시나리오를 데이터로 만들고 각 턴에 검증 규칙을 붙여 자동으로 재생하고 채점한다.

- Turn 5 이후의 모든 응답에 `@Qualifier`가 없을 것
- 3턴 뒤에도 해요체 유지
- Turn 7에서 답한 빈 이름이 로그와 일치

이 과제의 24턴 시나리오가 그 수동 버전이다. 자동화하면 실행 설정(모델 ID, 프롬프트 버전, 대화 구성)도 로그에 함께 남길 수 있다.

#### 세션 경계 설계

- 세션 종료 시점 (시간, 주제 변경)
- 재개 시 이력 복원 방법
- 여러 기기에서의 세션 공유 여부

#### 개인정보

대화 이력에 민감정보가 들어올 수 있으므로 보존 기간과 접근 통제를 정한다. (11번 참조)

### 이 과제와 현업의 차이

대화 구성과 입력을 사람이 손으로 실행했으므로 사람의 기록과 입력의 정확도에 의존했다.
자동 실행은 같은 입력을 정확히 전송하고 설정을 함께 기록해 이런 불확실성을 줄인다.

## 8. 비결정성

> 같은 입력에도 응답은 달라질 수 있으므로 한 번의 결과로 단정하지 않는다.

### 개념

#### 발생 원인

- 모델은 다음 단어를 확률적으로 선택한다(샘플링). 무작위성의 정도는 온도 같은 설정으로 조절된다.
- 설정을 낮춰도 완전히 같은 응답은 보장되지 않는다고 알려져 있다. 서빙 환경의 차이 등이 영향을 줄 수 있으며, 제공사와 모델마다 달라 공식 문서 확인이 필요하다.
- 모델이 업데이트되면 같은 이름이라도 결과가 달라질 수 있다.
- 사용자가 바꿀 수 있는 샘플링 설정의 범위도 제공사와 모델마다 다르다.

#### 변동의 종류

- 표현 변동: 같은 뜻을 다르게 표현. 대개 무해
- 내용 변동: 사실, 권고, 결정이 달라짐. 문제가 되는 변동

평가에서는 내용 변동을 본다.

#### 측정

같은 입력을 여러 번 실행해 통과 비율과 응답 일치율을 본다.
서로 다른 조건(새 대화와 같은 대화, 지침 유무)을 비교할 때는 다른 변수를 통제해야 한다.

### 이 과제에서는

- v1: 같은 입력인데 Turn 2에는 "`@Component`를 지우는 방법도 있다"가 있었고 Turn 4에는 없었음. 코드 조각 구성도 상이. 두 응답은 서로 다른 새 대화에서 나옴
- v2: 같은 대화 안에서 반복한 Turn 2와 4는 글자까지 동일
- 두 반복은 조건이 달라 "v2가 더 안정적"이라고 결론 내릴 수 없음. 각각 1회만 실행했다는 한계도 있음
- 샘플링 설정과 정확한 모델 ID는 기록하지 않음

### 현업에서는

#### 반복 평가 설계

- 케이스마다 N회 실행해 통과율 산출. N은 요구하는 신뢰 수준과 비용으로 결정하며 정해진 정답은 없음
- 통과율에 신뢰구간 병기. 20번 중 20번 통과해도 95% 신뢰구간의 하한은 약 84% (윌슨 구간)
- 변동이 큰 케이스를 따로 추려 원인 분석 (입력의 애매함, 규칙의 모호함)

#### 실행 정보의 고정과 기록

모델 ID(가능하면 버전이 고정된 ID), 샘플링 파라미터, 시스템 프롬프트 버전, 날짜와 시각을 응답과 함께 저장한다.

Anthropic 문서는 Claude 모델 ID가 고정된 버전(snapshot)을 가리킨다고 설명한다.
모델이 바뀌면 같은 프롬프트의 결과도 바뀔 수 있으므로 고정된 버전을 선호한다.

#### 모델 업데이트 관리

- 제공사의 모델 종료(deprecation) 일정 추적과 교체 계획 수립
- 새 모델은 섀도우 평가(운영 요청의 사본을 새 모델에도 보내 결과만 비교)나 점진 전환(카나리)으로 확인 후 교체

#### 변동을 흡수하는 설계

- 재시도: 형식이 틀리면 다시 요청
- 다수결: 여러 번 생성해 가장 많이 나온 답 채택 (비용 증가)
- 후처리 정규화: 표현 변동을 코드로 통일
- 허용 범위 설계: 표현은 달라도 되고 사실은 달라지면 안 됨

#### 운영 측면

제공사 호출의 실패, 지연, 호출 한도에 대비한 재시도와 대체 모델(또는 대체 제공사)도 같은 맥락에서 설계한다.

### 이 과제와 현업의 차이

조건마다 한두 번 실행했고 설정도 기록하지 않았다.
따라서 "v1에서는 달랐고 v2에서는 같았다"는 관찰은 변동성의 증거라기보다 추가 실행이 필요하다는 신호이다.

## 9. 프롬프트 개선 루프

> 관찰, 원인 파악, 최소 수정, 같은 지점의 재실행을 반복한다.

### 개념

#### 루프의 단계

관찰(로그에서 문제 찾기) → 원인 분류 → 가설 → 최소 수정 → 재실행 → 비교 → 기록

#### 원인 분류의 선행

같은 "틀렸다"도 원인에 따라 해결 방법이 다르다.

| 원인 | 해결 방향 |
|---|---|
| 지침이 모호하거나 빠짐 | 프롬프트 수정 |
| 지침은 있으나 어김 | 검증 단계 추가, 구조 변경 |
| 모델이 모르는 지식 | 근거 공급(검색), 사람 확인 |
| 평가가 잘못됨 | 평가 기준과 정답표 수정 |
| 우연한 변동 | 반복 실행으로 확인 |

#### 최소 수정

한꺼번에 여러 개를 바꾸면 무엇이 효과였는지 알 수 없다. 문제 하나에 규칙 하나로 대응하면 효과와 부작용을 분리해서 볼 수 있다.

#### 회귀

고쳤더니 원래 잘 되던 것이 깨지는 현상이다. 기존 항목(예: 틀린 전제를 바로잡는 능력)을 다시 확인한다.

#### 과적합

몇 개 사례에만 맞춰 고치면 다른 입력에서는 통하지 않는다. 개발용 데이터와 마지막 확인용 데이터를 따로 둔다.

#### 변경 기록

무엇을, 왜, 어떤 로그 근거로 바꿨는지 남겨야 나중에 되짚을 수 있다.

### 이 과제에서는

([system-design.md](system-design.md) §9)

| v1에서 본 문제 | v2의 대응 규칙 |
|---|---|
| 없는 공식 문서 제목 (Turn 2) | 금지 6: 문서 제목과 URL을 따옴표로 옮기지 않고 이름과 검색 키워드만 안내 |
| "같은 에러" 단정 (Turn 6) | 금지 7: 예외 클래스 이름으로 쓰고 메시지는 확실할 때만 |
| `@Primary`와 `@Qualifier`를 한 코드 블록에 (Turn 4) | 해결 힌트: 서로 대체되는 방법을 한 블록에 같이 넣지 않음 |
| 필터 확인 방법의 전제 미표시 (Turn 24) | 확인 방법: 선행 작업이 필요하면 "(전제: ...)"를 씀 |

- 수정 방식: 기존 규칙을 약화하지 않고 규칙 4개를 추가하는 최소 수정
- 재실행 결과: 문서 제목 미출현, 코드 블록 분리, 필터 확인의 전제 명시
- "같은 에러" 단정: Turn 6에서 재현되지 않아 추가 질문으로 확인. 예외 클래스만 답하고 메시지는 확인 필요로 남김
- 필터 확인: 전제는 밝혔으나 질문한 터미널 확인에는 직접 답하지 않아 미해결로 분류
- 한계: 규칙마다 1회만 실행

### 현업에서는

#### 개선 사이클 전체

```
운영 로그·사용자 피드백 → 실패 사례 분류 → 평가 데이터에 편입
        ↑                                         │
        │                                         ↓
   모니터링 ← 단계 배포 ← 리뷰 ← 자동 평가 ← 프롬프트·구조 수정
```

#### 변경 요청 단위의 작업

프롬프트 변경도 코드 변경과 같은 방식으로 제출한다. 변경 설명에 포함되는 항목은 다음과 같다.

- 해결하려는 문제와 근거 로그
- 변경 내용과 가설
- 평가 결과 (전후 비교, 회귀 여부)
- 위험과 되돌리는 방법

#### 자동 평가와 통과 조건(CI)

- 변경이 올라오면 평가 데이터셋을 자동 실행
- 전체 평가는 비용이 크므로 빠른 스모크 테스트 → 전체 평가 순으로 단계화
- 통과 조건 예: 치명 오류 0건, 형식 준수율 기준 이상, 기존 항목 점수 하락 없음, 비용과 지연 예산 이내
- 기준 미달 시 배포 차단

#### 단계 배포

| 방식 | 내용 |
|---|---|
| 섀도우 | 새 버전을 운영 요청의 사본에서 실행해 결과만 비교 (사용자에게 노출되지 않음) |
| 카나리 | 일부 사용자에게만 먼저 적용 |
| A/B | 두 버전을 나눠 지표 비교 |
| 롤백 | 문제 발생 시 이전 버전으로 즉시 복귀 |

기능 플래그로 켜고 끄는 방식을 쓰는 팀이 많다.

#### 관측

요청 하나가 거치는 단계(컨텍스트 조립, 모델 호출, 후처리)를 추적(trace)으로 기록하고 토큰, 지연, 비용, 오류율, 평가 점수를 대시보드로 확인한다.
Langfuse 같은 LLM 관측·평가 도구가 이 용도로 쓰인다.

#### 과적합 방지

개발용 데이터와 홀드아웃을 분리하고, 새로 나온 실패 사례를 계속 편입해 평가 데이터가 현실과 멀어지지 않게 한다.

#### 온라인 평가

사전 평가만으로는 실제 사용 패턴을 모두 알 수 없으므로 운영 중의 사용자 피드백과 지표로 효과를 확인한다.

### 이 과제와 현업의 차이

v2의 효과를 1회 실행으로 확인했고 평가 데이터셋과 홀드아웃도 없었다.
Turn 6의 문제는 재실행에서 재현되지 않아 효과를 판단할 수 없었다. 현업에서는 같은 평가를 반복 실행해 규칙의 효과를 가린다.

## 10. 프롬프트의 한계

> 프롬프트로 해결되지 않는 문제가 있으며, 이를 알아보고 알맞은 층에서 푸는 것이 설계 능력이다.

### 개념

#### 프롬프트가 해결하지 못하는 것

1. 지식의 한계: 모델이 모르는 사실은 프롬프트로 채워지지 않음
2. 강제력의 한계: 규칙을 적어도 어길 수 있음
3. 일관성의 한계: 같은 규칙이 매번 같은 방식으로 지켜지지는 않음
4. 요구 충돌: 두 요구를 동시에 만족하기 어려울 수 있음
5. 보안의 한계: 금지 문구가 공격을 막아 주지 않음

#### 알맞은 층에서 풀기

| 층 | 수단 | 적합한 문제 |
|---|---|---|
| 프롬프트 | 규칙, 예시 | 행동 방식, 말투, 형식 |
| 컨텍스트 | 검색, 사용자 정보 주입 | 지식 부족 |
| 시스템 설계 | 단계 분리, 검증, 재시도 | 강제력, 일관성 |
| 코드와 권한 | 검사 코드, 접근 제한 | 안전, 보안 |
| 사람과 절차 | 검토, 에스컬레이션 | 판단, 책임 |

문제를 프롬프트 한 층에서만 풀려고 하면 막힌다. 지식 부족을 규칙으로 해결하려는 경우가 그 예이다.

#### 요구 충돌의 해결 방법

- 우선순위 결정
- 요구의 분리 (질문에는 답하고 전제는 따로 안내)
- 질문의 재정의

### 이 과제에서는

([unresolved.md](unresolved.md))

1. 지시 충돌: "터미널 확인 질문에 답할 것"과 "안 배운 전제(필터 등록)를 쓰지 말 것"의 충돌. v1은 질문에 답했으나 전제가 숨어 있었고, v2는 전제를 지켰으나 질문에 직접 답하지 못함
2. 일관성: 우회 방법(구현체 삭제)을 쓰지 말라는 직접 금지 문장은 시도하지 않았고, 조건이 바뀌면 우회 방법이 다시 등장

모델이 문서 항목명이나 에러 메시지 문구 같은 사실을 모르는 문제는 프롬프트로 알려 줄 수 없어 출력 형식에 확인 필요 칸을 두었다. 모델은 모른다고 말하고 사람이 확인하는 분업이다.

### 현업에서는

#### 파이프라인 분해

한 번의 호출에 모든 요구를 넣지 않고 단계로 나눈다.

분류(정보가 충분한가) → 근거 검색 → 답변 생성 → 규칙 위반 검사 → 필요 시 재작성 → 사람에게 전달

충돌하는 요구는 단계로 나누면 풀리는 경우가 많다.
이 과제에 적용하면 답변 생성 단계는 질문에 답하고, 범위 검사 단계가 안 배운 전제의 혼입을 확인해 있으면 안내 문구를 덧붙이는 구성이다.

#### 가드레일

- 입력 쪽: 개인정보 탐지와 마스킹, 금지 주제 필터, 입력 길이 제한
- 출력 쪽: 형식 검사, 금칙어와 비밀 유출 검사, 정책 위반 시 대체 응답
- 출력을 다른 시스템에 넘길 때는 그대로 신뢰하지 않고 검증. OWASP LLM 목록의 Improper Output Handling이 이 문제에 해당 (2025판 LLM05, 2026판 LLM10)

#### 프롬프트는 보안 경계가 아니다

프롬프트 인젝션은 입력에 섞인 지시문이 모델의 행동을 조종하는 공격이다.
사용자가 직접 입력하는 경우도 있고 검색한 문서나 웹 페이지 속에 숨어 있는 경우(간접)도 있다.

권한과 도구 접근은 코드와 정책으로 제한한다(최소 권한).

- 모델이 수행할 수 있는 행동 자체를 축소
- 삭제, 결제, 외부 전송 같은 위험한 행동은 사람 승인 경유

OWASP LLM 상위 10대에서 Prompt Injection은 2025판과 2026판 모두 LLM01이고, 과도한 권한(Excessive Agency)은 2025판 LLM06, 2026판 LLM03이다.

#### 알려진 한계의 관리

- 알려진 문제 목록에 현상, 영향, 임시 대응, 담당자 기재
- 사용자 대상 한계 안내 문구와 에스컬레이션 경로(담당자 연결) 마련
- 위험 등록부에 등재하고 위험을 수용한 주체 기록

#### 투자 결정

프롬프트를 더 다듬을지, 구조를 바꿀지, 범위를 줄일지를 비용 대비 효과로 결정한다.
일부 한계는 "이 서비스는 그것을 하지 않는다"로 범위를 줄이는 것이 가장 저렴한 해결이다.

### 이 과제와 현업의 차이

이 과제는 입력(수강생 질문)을 신뢰할 수 있다고 가정했다.
실서비스에서는 사용자 입력을 신뢰하지 않는 것이 출발점이므로 프롬프트 인젝션과 권한 제한까지 설계에 포함된다.

## 11. 기록, 재현성, 거버넌스

> 실험은 다른 사람이 같은 조건으로 다시 확인할 수 있게 남겨야 하며, 기록도 검증 대상이다.

### 개념

#### 재현성의 세 층

1. 입력 재현: 같은 입력의 사용 가능 여부 (원문 보존)
2. 설정 재현: 같은 모델, 파라미터, 프롬프트 버전의 사용 가능 여부
3. 환경 재현: 같은 모델 버전의 존속 여부

LLM은 완전한 재현이 어려우므로(8번) 원문을 증거로 남기고 조건을 기록해 보완한다.

#### 기록 항목

입력 원문, 응답 원문, 모델 이름과 버전, 시각, 지침(프롬프트) 버전, 적용 방식, 설정값, 대화 구성(같은 대화인지 여부)

#### 증거와 해석의 구분

원문은 편집하지 않고 해석과 판정은 따로 적는다. 판정이 틀렸을 때 원문으로 다시 따질 수 있어야 한다.

#### 기록의 검증

기록을 만든 뒤 원본과 대조하고 틀린 곳은 숨기지 않고 정정하면서 이유를 남긴다.

### 이 과제에서는

- 대화 로그: 편집 없이 원문 그대로 보존
- 실행 정보: 모델, 시각, 지침 적용 방식, 스크린샷 기록
- 확인과 추정의 구분: "환각 확정"과 "의심", 시각의 "추정"과 "확인"
- 결과 해석에 영향을 주는 조건(반복 확인이 새 대화에서 이뤄진 점 등)을 기록 앞부분에 명시 ([run-log.md](run-log.md) §3)

### 현업에서는

#### 로깅 설계

- 대상: 요청, 응답, 모델 ID, 프롬프트 버전, 설정값, 시각, 지연, 토큰 수, 평가 점수, 사용자 피드백
- 저장소: 관측 플랫폼이나 로그 저장소 (구조화해서 검색 가능하게)
- 접근: 권한과 열람 이력(감사 로그) 관리

사람이 손으로 적던 실행 정보를 자동 기록으로 대체하는 것이 핵심이다.

#### 개인정보와 기밀

이 과제의 "원문 그대로 보존" 규칙은 가상 예시 데이터이기 때문에 가능했다.
실제 수강생의 이름, 코드, 로그가 포함되면 그대로 보관하기 어려운 경우가 많다.

- 수집 최소화: 꼭 필요한 것만 저장
- 마스킹과 가명화: 이름, 이메일, 키, 식별자를 가려서 저장
- 보존 기간과 삭제 요청 대응 규정
- 암호화와 접근 통제

원문 보존은 증거 원칙이고 민감정보 비보존은 데이터 보호 원칙이어서 두 원칙이 충돌한다. 현업에서는 마스킹한 원문을 보존하는 방식으로 조정한다.

#### 벤더(모델 제공사) 관리

외부 모델 API로 보내는 데이터의 취급은 요금제와 계약마다 다르다.

- 확인 항목: 저장 여부, 학습 사용 여부, 보존 기간, 데이터 처리 지역
- 약관과 데이터 처리 계약(DPA), 보안 인증, 하위 처리자 정보 확인
- 개인용 무료 요금제에 업무 데이터를 넣지 않는 것이 흔한 규칙

#### 거버넌스 체계

- AI 시스템 목록: 조직에서 쓰는 AI 기능의 목록 관리 (용도, 담당자, 모델, 데이터)
- 위험 등급과 승인 절차: 용도의 위험도에 따라 검토 수준이 달라짐
- 문서화: 모델과 시스템의 목적, 한계, 평가 결과 기록 (모델 카드, 시스템 카드 같은 형식)
- 사고 대응: 잘못된 응답으로 문제가 생겼을 때의 보고, 원인 분석, 재발 방지 절차
- 정기 검토: 모델, 데이터, 규제 변화에 따른 주기적 재점검

#### 감사 대응

"어느 시점에 어떤 버전이 어떤 입력에 어떤 출력을 냈는가"를 재구성할 수 있어야 한다. 앞의 기록이 이를 가능하게 한다.

### 이 과제와 현업의 차이

실행 정보를 사람이 손으로 적었다. 자동 기록이라면 누락과 오류의 가능성이 낮다.
이 과제는 증거 원칙(원문 보존)을 우선했으나 실제 데이터를 다룬다면 데이터 보호 원칙과의 조정이 필요하다.

## 부록 A. 규모별 차이

| 구분 | 개인·소규모 실험 | 팀 단위 서비스 | 엔터프라이즈 |
|---|---|---|---|
| 평가 | 수작업, 소규모 | 평가 데이터셋 + 자동 채점 | 복수 평가자, 정기 재평가, 감사 가능 |
| 프롬프트 | 문서나 화면에 보관 | 저장소 버전 관리 | 배포 단계, 변경 승인 |
| 실행 | 수동 | 스크립트, CI | 파이프라인, 모니터링 |
| 안전 | 사람이 최종 검토 | 출력 검증, 에스컬레이션 | 권한 통제, 레드팀, 위험 관리 체계 |
| 데이터 | 가상 데이터 | 마스킹, 접근 제어 | 계약, 보존·삭제 정책, 규제 대응 |
| 조직 | 한 사람이 여러 역할 | 개발·평가·운영 분담 | 전담 역할, 승인 위원회 |

이 과제는 왼쪽 열에 해당한다. 오른쪽으로 갈수록 사람이 눈으로 확인하던 것이 코드와 절차로 옮겨진다.

## 부록 B. 용어집

| 용어 | 뜻 |
|---|---|
| 프롬프트 | 모델에 주는 입력(지시, 질문, 예시) |
| 시스템 프롬프트 | 대화 전체에 적용되는 규칙 |
| 페르소나 | 역할, 말투, 전문 분야 설정 |
| Zero-shot, Few-shot | 예시 없이, 예시를 붙여서 시키는 방식 |
| 맥락 속 학습 | 프롬프트 안의 예시로 해당 대화에서만 행동을 맞추는 것 |
| CoT | 단계별 추론을 유도하는 기법 |
| 컨텍스트 윈도우 | 모델이 한 번에 볼 수 있는 입력 길이의 한도 |
| 컨텍스트 조립 | 시스템 규칙, 근거, 이력, 질문을 합쳐 입력을 만드는 일 |
| 루브릭 | 점수를 매기는 기준표 |
| 정답표 | 사전에 적어 둔 정답과 틀린 답의 목록 |
| 홀드아웃 | 튜닝에 쓰지 않고 마지막 확인에만 쓰는 평가 데이터 |
| LLM 채점자 | 모델을 채점자로 쓰는 평가 방식 |
| 채점자 간 일치도 | 여러 채점자가 같은 판정을 내리는 정도 |
| 신뢰구간 | 측정값의 불확실성 범위 |
| RAG | 문서를 검색해 그 내용을 근거로 답하게 하는 방식 |
| 환각 | 그럴듯하지만 사실이 아닌 내용을 말하는 것 |
| 아첨 | 사용자의 틀린 말에 맞장구치는 경향 |
| 비결정성 | 같은 입력에도 결과가 달라지는 성질 |
| 회귀 | 고치다가 원래 잘 되던 것이 깨지는 것 |
| 과적합 | 특정 사례에만 맞춰져 다른 입력에서는 통하지 않는 상태 |
| 프롬프트 인젝션 | 입력 속 지시문이 모델의 행동을 조종하는 공격 |
| 가드레일 | 입력과 출력을 검사해 정책 위반을 막는 장치 |
| 섀도우, 카나리, A/B | 새 버전을 안전하게 확인하는 배포 방식 |
| 폴백 | 실패했을 때 쓰는 대체 응답이나 대체 경로 |
| 관측 | 요청의 흐름과 지표를 기록하고 분석해 상태를 파악하는 것 |
| 재현성 | 같은 조건으로 다시 해서 같은 결과를 확인할 수 있는 성질 |

## 한 문장 요약

LLM에게 일을 맡길 때는 판정 방식을 먼저 정하고, 결과를 원문 그대로 남기고, 틀린 곳은 근거를 확인한 뒤 최소한으로 고치고, 고쳐지지 않는 것은 한계로 기록한다.
현업에서는 같은 일을 사람의 눈 대신 코드와 절차로 반복할 수 있게 만든다.
