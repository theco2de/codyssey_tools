# 산출물 4. 미해결 기록

> 프롬프트를 고쳐도 **끝내** 원하는 결과가 나오지 않은 과업만 적는다. 성공한 시도는 적지 않는다.
> "막힌 이유"는 **직접 작성**한다. (원인을 정확히 못 짚어도, 무엇을 시도했고 어디서 멈췄는지 적으면 충족)
> 이 문서의 각 항목은 초안이다. 시도 횟수가 적으므로 확정 전에 직접 확인하고 고친다.

---

## [미해결 1] 진도 범위를 지키면서 "터미널로 필터 동작 확인"에 답하기

### 원하는 결과

"필터가 동작하는지 터미널에서 확인하는 방법"이라는 질문에 직접 답하되, 수강생이 아직 안 배운 내용(필터를 스프링에 등록하는 방법)을 전제하지 않는 확인 방법을 주는 것.

### 시도한 프롬프트

**시도 1** (시스템 프롬프트 v1 + 입력 템플릿, run-log.md Turn 23)
```text
블로그 보고 필터를 만들어 보려고 import javax.servlet.Filter; 를 썼는데 IntelliJ에서 빨간 줄이 떠요. 의존성 문제인가요? 그리고 필터가 동작하는지 터미널에서 확인하는 방법도 알려주세요.
```

**시도 2** (시스템 프롬프트 v2에서 추가한 규칙 + 같은 입력, run-log.md §4 Turn 23)
```text
확인 단계가 등록·설정 같은 선행 작업을 전제로 하면, 그 단계 안에 "(전제: ...)"를 쓴다. 수강생이 아직 안 배운 전제라면 그 단계 대신 배운 범위의 확인 방법(IDE 빨간 줄, 빌드 성공 여부 등)을 쓴다.
```

### 받은 결과 (요약 + 원문 위치)

- 시도 1 (run-log.md Turn 24): `jakarta` 변경은 맞게 안내했다. 확인 방법으로 필터에 로그를 넣고 `Invoke-WebRequest`로 요청해 콘솔 로그를 보라고 했지만, 필터가 스프링에 등록돼 있어야 동작한다는 전제는 `확인 필요`에서만 밝혔다. 따라 하면 로그가 안 찍힐 수 있다.
- 시도 2 (run-log.md §4 Turn 24): 전제를 밝히고 "터미널로 필터 동작을 확인하는 방법은 지금은 안내하기 어려워요"라고 답했다. 빨간 줄이 사라지고 빌드가 성공하는지까지만 확인하라고 했고, 터미널 확인은 `Invoke-WebRequest`를 쓸 수 있다는 한 문장만 덧붙였다.
- 각각 한 번씩만 실행했다.

### 막힌 이유 (직접 작성)

(초안, 추정) 시도 1은 질문에 직접 답했지만 전제가 숨어 있었고, 시도 2는 전제를 지켰지만 질문에 직접 답하지 못했다. 두 요구("질문에 답한다"와 "안 배운 전제를 쓰지 않는다")가 한 응답 안에서 충돌하는 것으로 보이는데, 규칙 문장만으로 이 균형을 맞추지 못했다. 정확한 원인은 확인하지 못했다. 시도는 2번뿐이다.

## [미해결 2] 대체 방법 중 "구현체 삭제" 같은 우회 방법을 일관되게 빼기

### 원하는 결과

같은 에러에 대해 대체 방법을 안내할 때, 구현체의 `@Component`를 지우는 식의 우회 방법은 해결책으로 제시하지 않는 것(정답표 §5에서 "구현체 하나를 지우라는 것만 제시"는 틀린 답으로 본다).

### 시도한 프롬프트

**시도 1** (시스템 프롬프트 v1, 우회 방법에 대한 규칙 없음. run-log.md Turn 1~6)
```text
해결 힌트: 어디를 어떻게 고치면 되는지. 코드 조각은 3줄 이하.
```

**시도 2** (시스템 프롬프트 v2에서 추가한 문장, run-log.md §4)
```text
해결 방법이 여러 개면 가장 먼저 시도할 한 가지만 코드로 보이고, 나머지는 문장으로만 쓴다. 서로 대체되는 방법을 한 코드 블록에 같이 넣지 않는다.
```

### 받은 결과 (요약 + 원문 위치)

- 시도 1: Turn 2에서 "그 클래스의 `@Component`를 지우는 방법도 있어요"가 나왔고, Turn 4와 Turn 6에는 없었다(run-log.md Turn 2, 4, 6). 같은 입력인데 새 대화마다 달랐다(Turn 2는 대화 A, Turn 4와 6은 대화 B).
- 시도 2: Turn 2와 4(같은 입력, 같은 대화 안에서 반복)는 글자까지 같았고 우회 방법이 없었다. 그러나 `@Qualifier` 금지 조건을 준 Turn 6에서 "지금 당장 한 가지 구현체만 필요하다면, 쓰지 않는 쪽의 `@Component`를 지워서 빈을 하나만 남기는 방법도 있어요"가 다시 나왔다(run-log.md §4 Turn 6).
- 시도 2의 문장은 "코드를 한 가지만 보이라"는 규칙이라 우회 방법 자체를 막지는 않는다. 우회 방법을 직접 금지한 문장은 시도하지 않았다.

### 막힌 이유 (직접 작성)

(초안, 추정) 해결 방법의 개수를 줄이는 규칙은 넣었지만 "우회 방법을 쓰지 않는다"는 직접 금지는 시도하지 않았고, 조건(`@Qualifier` 금지)이 바뀌면 후보가 줄어들면서 우회 방법이 다시 나타났다. 같은 입력의 실행마다 달라지는 변동성도 있어서, 한두 번의 실행으로는 규칙이 효과가 있는지 판단하기 어려웠다. 직접 금지 문장을 넣은 v3를 실행해 보면 더 분명해질 것이다.
